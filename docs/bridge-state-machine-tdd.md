# Bridge 行为测试方法

本文只规定验证方法。功能和生命周期要求由 [ACP → bridge 内存合同](acp-fidelity-audit.md#9-acp-to-bridge-memory-contract)定义，实施顺序与门禁见[实现计划 §7](state-sync.md#7-fidelity-migration-revision-2)；前端与 bridge 的同步、校验和修正要求见[协议 §12](protocol.md#12-synchronization-design-requirements)。旧合同与测试结果见[历史索引](history.md)。

## 验证顺序

先以协议输入建立可复现的失败行为，再修复实现并保持原断言。先验证真实 ACP 入口、bridge 权威内存和答复，再验证发布与前端。只有测试夹具或合同本身有误时才更正断言，并说明依据；不能通过忽略测试、接受失败退出或放宽断言使修复通过。

具体用例和当前实现差距只维护在上述权威文档中，不在这里复制第二份能力清单。

## 十项测试方法

1. **直接检查权威状态。** 用标准 ACP fixture 驱动真实 coordinator，独立检查收到的输入、内存语义、实际答复与可读取的资源。至少包含没有前端订阅的场景。两个副本或投影彼此相等不能证明它们没有共同丢失数据。

2. **确定性控制交错。** 在真实 ingress、FIFO、发送和 completion 边界设置屏障；期限使用暂停时钟。测试只暂停生产操作，不替实现修改状态，也不依赖墙钟 sleep。生产实现消除竞态窗口后，移动屏障而不是为了测试重建窗口。

3. **检查顺序与取消。** 覆盖发送登记与快速响应、通知与响应同批到达、响应与 EOF 竞争，以及取消前后的有效更新。检查答复只结清一次，取消意图不被当作原操作已经完成；外部等待期间其他允许的请求和会话仍能推进。

4. **检查加载事务。** 候选在成功前不可见，响应切点之后的更新不能越过安装；失败、非法重放、取消及迟到完成只影响自己的加载 attempt。检查原有状态保持完整，也检查后续合法加载能成功。重放历史工具或交互内容不能凭空创建可回答的 responder。

5. **逐项证明资源结清。** 成功、错误、取消、断线和任务释放都覆盖到真实句柄、等待者及关联登记。验证恰好释放自身资源、不影响后继或其他会话、不泄漏永久忙状态。取消 token 已触发不等于收尾已完成；前端断开场景直接检查已准入工作的实际结果。

6. **用对照样本检查内存成本。** 增大无关已保留正文，再执行相同的小更新，比较新增分配和发布量。旧视图应不可变，非法更新不留下部分修改或错误计费。计量只包住生产调用，不把夹具构造、断言或测试序列化算进去。

7. **验证消费交接的最后一次更新。** 在消费者已领取旧 payload、新状态尚未发布的边界暂停，交错执行后不再发送任何新更新。新状态必须已包含在本次交付或留有下一次可领取事件。替换、消费、释放后的计费应恰好结清；不能用弱引用仍存活推断消费者仍会读取。

8. **验证完整性和合法边界。** 使用大消息、突发通知、长历史和慢订阅者，检查源内容与最终内存一致，不因任意累计限额静默丢失。另测 Agent 显式输出限制、协议字段域、协商能力和文件根目录限制，区分合法约束与实现额外限制。同步队列合并的正确性在第二阶段单独验证。

9. **验证自然 EOF 的有序收尾。** 令 Agent 在发送完整片段及最终响应后立即退出，检查已接收前缀和结果不会被清理覆盖；再测响应缺失时的真实中断状态。收尾错误不得把已收到结果改成虚构成功，或用后续 broken pipe 掩盖原始结果。

10. **说明证据能证明什么。** 原生内存分配测试不等于 RSS、峰值或 CPU 上限；静态样例不是 ACP 生命周期覆盖；旧版本通过数不代表当前版本通过。修复须同时保留负向断言和正向进展断言，再运行受影响层的现有检查；前端验收不能替代 bridge 门禁。

## 用例记录

每项回归只记录输入及能力前提、确定性交错、预期内存与答复、资源结束条件和验证结果。测试命名描述可观察行为，避免把内部容器、身份字段或特定 Agent 的实现方式写成合同。测试命令及环境条件统一见[验证说明](testing.md)。
